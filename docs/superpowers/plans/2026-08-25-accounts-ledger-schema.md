# Accounts & Financial Ledger Schema Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the `Account`/`AccountTransaction` models and the `MANAGE_ACCOUNTS` permission
on top of the existing domain schema, so a later Finance module implementation plan has
somewhere for `Payment`/`Expense`/`Refund` money to actually go.

**Architecture:** Pure data-layer change, same shape as the earlier domain-schema-foundation
plan. Add 2 new models (`Account`, `AccountTransaction`) and 2 new enums (`AccountType`,
`AccountTransactionType`) to `Server/prisma/schema.prisma`, add a back-relation to each of
`Payment`/`Expense`/`Refund`, generate and apply a Postgres migration, and extend
`adminSeed.js` with the one new permission. No routes, controllers, services, or frontend
code in this plan — Account catalog CRUD and wiring `Payment`/`Expense`/`Refund` creation to
require an account are the future Finance module implementation plan's job, per the spec's
explicit "Out of scope."

**Tech Stack:** Prisma ORM 7 (`prisma-client-js` generator, Postgres datasource), Node.js seed
script (`Server/cmd/Seed/adminSeed.js`), no test framework in this repo — verification is
migration success + a manual Prisma Client query pass, matching how the original domain
schema plan was verified.

**Spec:** `docs/superpowers/specs/2026-08-25-accounts-ledger-design.md`

## Global Constraints

- `Account` holds no `currency` field — an account can carry balances in either/both
  supported currencies (`USD`, `INR`); currency lives on each `AccountTransaction` row, not
  on `Account`.
- Balance for `(account, currency)` is **always derived** (`SUM` of credit-type
  `AccountTransaction.amount` minus `SUM` of debit-type, filtered by `currency`) — never a
  cached field on `Account`.
- `AccountTransaction.amount` is always positive; direction is implied by `type`:
  `OPENING_BALANCE`/`PAYMENT_RECEIVED` are credits, `EXPENSE_PAID`/`REFUND_ISSUED` are debits.
- `AccountTransaction.{paymentId,expenseId,refundId}` are each optional and `@unique` — at
  most one is set per row (a 1:1 pairing with whichever record caused the entry), all three
  are null for an `OPENING_BALANCE` entry. Same independent-optional-FK pattern this schema
  already uses for `Expense.caseId`/`Expense.visaApplicationId`.
- All new `Decimal` money fields use `@db.Decimal(12, 2)`, matching the existing fix already
  applied to `HospitalInquiry.treatmentCostEstimate`/`Payment.amount`/`Expense.amount`/
  `Refund.amount` (see commit `ce69808`).
- Relations that guard financial-integrity data get `onDelete: Restrict` at the DB level,
  matching the existing convention on `Case.agency`/`Expense.case`/`Expense.visaApplication`
  (see commit `ce69808`) — applies to all four of `AccountTransaction`'s relations
  (`account`, `payment`, `expense`, `refund`).
- No test framework exists in this codebase (`Server/package.json`'s `test` script is a
  stub). Verification in this plan is: migration applies cleanly, `npx prisma generate`
  succeeds, and a manual Prisma Client script confirms the new tables/permission exist.
- Follow the existing seed pattern in `Server/cmd/Seed/adminSeed.js` (`Prisma.x.upsert`,
  idempotent, connects new permissions to the `ADMIN` role) — do not introduce a different
  seeding mechanism.
- This plan is schema-only. No API routes, controllers, services, frontend pages, or Account
  CRUD of any kind — that's the Finance module implementation plan's job, once it exists.

```prisma

// ---------- Accounts & ledger ----------

model Account {
  id       String      @id @default(cuid())
  name     String      @unique
  type     AccountType
  isActive Boolean     @default(true)
  notes    String?

  transactions AccountTransaction[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

model AccountTransaction {
  id        String  @id @default(cuid())
  accountId String
  account   Account @relation(fields: [accountId], references: [id], onDelete: Restrict)

  type     AccountTransactionType
  amount   Decimal @db.Decimal(12, 2)
  currency Currency
  notes    String?

  paymentId String?  @unique
  payment   Payment? @relation(fields: [paymentId], references: [id], onDelete: Restrict)

  expenseId String?  @unique
  expense   Expense? @relation(fields: [expenseId], references: [id], onDelete: Restrict)

  refundId String?  @unique
  refund   Refund?  @relation(fields: [refundId], references: [id], onDelete: Restrict)

  createdAt DateTime @default(now())
}

// ---------- Enums ----------
```

### Task 2: Generate and apply the migration

**Files:**
- Create: `Server/prisma/migrations/<timestamp>_add_accounts_and_ledger/migration.sql` (generated, not hand-written)

**Interfaces:**
- Consumes: `Server/prisma/schema.prisma` from Task 1.
- Produces: a migrated Postgres database with the `Account`/`AccountTransaction` tables and
  the two new enum types, and a regenerated Prisma Client exposing `Prisma.account`/
  `Prisma.accountTransaction` — the future Finance module plan depends on these existing.

- [ ] **Step 1: Confirm the dev database is reachable**

Run (from `Server/`): `npx prisma db pull --print`
Expected: prints the current live schema without erroring. If this fails, stop and resolve
the connection issue before continuing.

- [ ] **Step 2: Generate and apply the migration**

Run (from `Server/`): `npx prisma migrate dev --name add_accounts_and_ledger`
Expected: output ends with `Your database is now in sync with your schema.` and
`✔ Generated Prisma Client`. A new folder appears under `Server/prisma/migrations/` named
`<timestamp>_add_accounts_and_ledger` containing `migration.sql`.

- [ ] **Step 3: Spot-check the generated SQL**

Read the new `migration.sql` file. Confirm it contains:
- `CREATE TYPE "AccountType"` and `CREATE TYPE "AccountTransactionType"`
- `CREATE TABLE "Account"` with columns `id`, `name`, `type`, `isActive`, `notes`,
  `createdAt`, `updatedAt`
- `CREATE TABLE "AccountTransaction"` with columns `id`, `accountId`, `type`, `amount`,
  `currency`, `notes`, `paymentId`, `expenseId`, `refundId`, `createdAt`
- Unique indexes on `AccountTransaction.paymentId`, `AccountTransaction.expenseId`,
  `AccountTransaction.refundId`, and `Account.name`
- Four `FOREIGN KEY` constraints on `AccountTransaction` (`accountId` → `Account`,
  `paymentId` → `Payment`, `expenseId` → `Expense`, `refundId` → `Refund`), each with
  `ON DELETE RESTRICT`

If any are missing, Task 1's schema edit was incomplete — fix `schema.prisma`, then run
`npx prisma migrate dev` again (it detects the schema changed and generates a corrective
migration).

## What comes after this plan

This plan only lands the schema. The Finance module still needs its own implementation
plan (Payment collection, Expense recording, Refund issuance, and now: Account catalog CRUD
gated by `MANAGE_ACCOUNTS`, plus wiring every Payment/Expense/Refund creation to require
picking an account and atomically writing its paired `AccountTransaction` in the same
`Prisma.$transaction` — the pattern already established by the Cases module's `sendInquiry`/
`respondToInquiry`). Bring that back through brainstorming for its own short spec update
(or fold into the existing Finance section of the original domain schema spec) before
